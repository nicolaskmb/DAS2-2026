# ADR-003: Escolha da Biblioteca de Acesso ao Banco de Dados para Extração de Dados

**Status:** Aceito
**Data:** 2026-06-09
**Autores:** Nicolas, Jorge, Thales, Vladimir

---

## Contexto

A arquitetura da solução utiliza Azure Functions para executar rotinas de extração de dados do ERP e disponibilizá-los para processamento posterior.

Durante o desenvolvimento decidimos testar duas abordagens diferentes:

* **pyodbc** (driver nativo para SQL Server)
* **SQLAlchemy** (ORM/Data Access Layer)

Para embasar a decisão, foi desenvolvida uma Prova de Conceito (PoC) executada dentro do projeto Azure Functions, utilizando a mesma consulta SQL, o mesmo banco de dados e a mesma tabela.

A consulta utilizada foi:

```sql
SELECT TOP 5 * FROM erp.pedido_item
```

Cada implementação executou a consulta duas vezes, medindo o tempo necessário para conectar ao banco, executar o SELECT e carregar todos os registros em memória.

---

## Decisão

Foi decidido adotar o **SQLAlchemy** como biblioteca padrão para acesso ao banco de dados na camada de extração.

Embora o pyodbc seja um driver nativo com menor nível de abstração, os testes demonstraram desempenho superior do SQLAlchemy no cenário avaliado.

### Resultado da PoC

| Biblioteca | Execução 1 | Execução 2 | Média      |
| ---------- | ---------- | ---------- | ---------- |
| pyodbc     | 0,716228 s | 0,453177 s | 0,584702 s |
| SQLAlchemy | 0,651721 s | 0,031727 s | 0,341724 s |

Diferença observada:

* SQLAlchemy apresentou tempo médio aproximadamente **41,5% menor** que o pyodbc.
* Ambas as abordagens utilizaram o mesmo banco, mesma consulta e mesma volumetria.

Além do resultado de desempenho, o SQLAlchemy oferece maior flexibilidade para evolução futura da aplicação, melhor organização do código e abstração da camada de acesso a dados.

---

## Consequências

### (+) Benefícios

* Melhor desempenho médio observado na PoC
* Código mais organizado e de fácil manutenção
* Facilidade para evolução futura do projeto
* Menor acoplamento ao driver específico do banco
* Melhor legibilidade e reutilização de código

### (-) Pontos negativos

* Dependência adicional de uma biblioteca externa
* Curva de aprendizado ligeiramente maior

---

## Alternativas rejeitadas

### pyodbc

Rejeitada como solução principal devido ao desempenho inferior observado nos testes realizados.
